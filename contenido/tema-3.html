Tema 3: TAD, Memoria y Estructuras Lineales

1. Tipos Abstractos de Datos (TAD) y Encapsulación

Cuando empezamos a programar un videojuego en Unity, es muy tentador pensar inmediatamente en cómo vamos a guardar los datos físicamente: «¿uso un array de enteros para el inventario?, ¿y si luego necesito guardar más objetos?». Sin embargo, obligarnos a decidir todos los detalles físicos de almacenamiento en una fase tan temprana complica innecesariamente el diseño. Si más adelante modificamos esa estructura para que el juego vaya más fluido, corremos el riesgo de que el resto de nuestros scripts dejen de funcionar.

Para evitar este problema, en ingeniería de software separamos qué hace un conjunto de datos de cómo se guarda en memoria mediante el uso de Tipos Abstractos de Datos (TAD).

1.1. TAD, Tipo de Datos y Estructura de Datos

Aunque en el día a día a veces se usan como sinónimos, es fundamental distinguir tres conceptos clave:

  • Tipo Abstracto de Datos (TAD): Es el modelo matemático de una colección de objetos de datos junto con las operaciones que manipulan esos objetos. Por ejemplo, el TAD CONJUNTO define una colección de elementos con operaciones como la unión, la intersección o la diferencia, sin importar en qué lenguaje se programe.
  • Tipo de Datos: Es la traducción de la especificación de un TAD a la sintaxis de un lenguaje concreto (como C#). Se compone de las variables necesarias para definir los datos y de los métodos o rutinas de acceso que implementan las operaciones del TAD.
  • Estructura de Datos: Es la colección física de variables en la memoria que están relacionadas de una forma específica (por ejemplo, casillas contiguas en un array o nodos enlazados por referencias). Nuestro objetivo es usar la estructura de datos que implemente cada TAD de la forma más eficiente posible.

C# ya nos ofrece tipos de datos predefinidos. Por ejemplo, el tipo int implementa el concepto matemático de número entero (el TAD ENTERO, formado por la unión de $\{-1, -2, \dots, -\infty\}$ y $\{0, 1, 2, \dots, \infty\}$ junto con operaciones como suma, resta, multiplicación y división entera). Observa que en matemáticas los enteros son infinitos, pero en la memoria de un ordenador eso es imposible: al implementar el tipo int en C# se decidió usar 32 bits en formato complemento a dos, acotando su rango entre $-2.147.483.648$ y $2.147.483.647$. Cuando un juego requiere estructuras que el lenguaje no trae de fábrica, construimos tipos de datos definidos por el usuario.

1.2. Visión Lógica vs. Visión de Implementación

Al crear nuestros propios tipos de datos en Unity trabajaremos siempre desde dos puntos de vista:

  • Visión lógica (Diseño): Es la que usamos al diseñar el juego. Define qué representa el TAD y qué operaciones ofrece al exterior (por ejemplo, una mochila donde podemos meter objetos, sacarlos y mirar cuántos hay). Solo debe existir una visión lógica.
  • Visión de implementación (Memoria y Eficiencia): Considera cómo se representan los datos en la memoria RAM y cómo están programados los métodos de acceso por dentro. Para una misma visión lógica pueden existir varios enfoques de implementación distintos (por ejemplo, programar la mochila por dentro con un array fijo o con nodos dinámicos).

1.3. Encapsulación en C# (private vs. public)

Hasta ahora no hemos puesto a penas diferencia entre cuando usar variables private o public. Un script de nuestro juego (como el controlador del personaje) debería manipular un tipo de datos únicamente en función de su visión lógica, nunca tocando directamente su almacenamiento físico. Aquí es donde ambas etiquetas cobran un papel importante:

Esta separación se conoce en ingeniería de software como encapsulación de datos u ocultación de la información. En C#, encapsulamos declarando las estructuras internas como private y construimos el acceso mediante métodos public. Esto nos aporta dos ventajas enormes:

  1. Facilidad de modificación: Mientras no cambiemos el nombre ni los parámetros de los métodos public, podemos reemplazar por completo la estructura de datos interna para optimizar el rendimiento sin romper ni una sola línea de código del resto del videojuego.
  2. Reutilización: Un TAD bien encapsulado se puede copiar y pegar en nuestro próximo proyecto de Unity y funcionará de inmediato sin que tengamos que recordar cómo estaba programado por dentro.

1.4. Especificación e Implementación de nuestro primer TAD: La Mochila

Para especificar un TAD antes de programarlo, basta con describir dos partes: sus objetos de datos y las operaciones que actúan sobre ellos.

Especificación: EL TAD MOCHILA

Objetos de datos: Una colección lineal de nombres de objetos (string) con una capacidad máxima de $N$ huecos.

Operaciones (métodos de acceso):

  • Guardar(item): Si la mochila no está llena, añade el objeto en el primer hueco disponible y devuelve true; si está llena, devuelve false.
  • SacarUltimo(): Si no está vacía, extrae y devuelve el último objeto guardado.
  • VerCantidad(): Devuelve el número entero de objetos almacenados actualmente.
  • EstaVacia() / EstaLlena(): Indica si hay $0$ objetos o si hemos alcanzado la capacidad $N$.

Veamos cómo traducimos esta especificación a C# encapsulando con private:

public class MochilaTAD {
    // === ENCAPSULACIÓN ===
    // Nadie fuera de esta clase puede tocar directamente este array ni el contador
    private string[] huecos;
    private int cantidadActual;

    // Constructor: inicializa la estructura interna con capacidad máxima N
    public MochilaTAD(int capacidadMaxima) {
        huecos = new string[capacidadMaxima];
        cantidadActual = 0;
    }

    // === MÉTODOS DE ACCESO ===
    public bool EstaVacia() {
        return cantidadActual == 0;
    }

    public bool EstaLlena() {
        return cantidadActual == huecos.Length;
    }

    public int VerCantidad() {
        return cantidadActual;
    }

    public bool Guardar(string nuevoItem) {
        if (EstaLlena()) {
            return false; // No cabe más en la mochila
        }
        huecos[cantidadActual] = nuevoItem;
        cantidadActual++;
        return true;
    }

    public string SacarUltimo() {
        if (EstaVacia()) {
            return null;
        }
        cantidadActual--;
        string itemExtraido = huecos[cantidadActual];
        huecos[cantidadActual] = null; // Limpiamos la casilla
        return itemExtraido;
    }
}

2. Modelo de Memoria: ¿Estructuras Estáticas o Dinámicas?

Para decidir la estructura de datos de nuestros TADs, necesitamos comprender cómo organiza la memoria un ordenador cuando ejecutamos un juego en Unity.

2.1. Memoria Principal (RAM) vs. Almacenamiento Secundario (Disco)

La memoria se divide en dos grandes niveles:

  • Memoria principal (RAM): Posee acceso directo. Esto significa que leer o escribir en cualquier posición de la memoria RAM tarda una cantidad de tiempo fija $O(1)$, independiente de las posiciones a las que hayamos accedido antes. Como es varios órdenes de magnitud más rápida que el disco duro, aquí residen las estructuras que usamos durante la partida, llamadas estructuras de datos internas.
  • Almacenamiento secundario (SSD / Disco): Se utiliza para guardar datos demasiado grandes para caber de golpe en la RAM o que deben conservarse al cerrar el juego (partidas guardadas, bases de datos de ítems, mundos abiertos en streaming). A estas las llamamos estructuras de datos externas. En esta asignatura nos centraremos siempre en las estructuras de datos internas.

2.2. El Mapa Lógico de la Memoria Principal

Podemos imaginar la memoria RAM de nuestro juego como un gran vector unidimensional de bytes dividido en tres zonas fundamentales:

MEMORIA ESTÁTICA (Zona Alta)
Tamaño fijo decidido al compilar (variables globales/estáticas)
MEMORIA LIBRE / MONTÍCULO (Heap)
Asignación dinámica en plena partida (Listas, Colas, Nodos con new)
↓ Crece hacia abajo ↓
Espacio disponible en RAM
↑ Crece hacia arriba ↑
PILA DE EJECUCIÓN (Call Stack - Zona Baja)
Registros de activación de funciones y llamadas recursivas
  1. Memoria Estática: Su espacio queda fijado durante la compilación y no cambia en toda la partida.
  2. Pila de Ejecución (Call Stack): Como vimos en el Tema 2 al estudiar la recursividad, cada vez que llamamos a una función se crea un registro de activación en la pila con sus parámetros, variables locales y la dirección a la que debe volver el programa al terminar. Cuando la función acaba, su registro se destruye automáticamente y la pila mengua.
  3. Memoria Libre (o Montículo / Heap): Aquí es donde se reserva espacio para las estructuras de datos que se crean en mitad de la ejecución del videojuego (cada vez que usamos la palabra clave new para crear nodos, listas, enemigos, etc.).

Observa que la Memoria Libre y la Pila de Ejecución crecen la una contra la otra. Si un juego hace infinitas llamadas recursivas (Stack Overflow) o si pide memoria dinámica sin parar y nunca la devuelve (Out of Memory), ambas zonas chocan y el videojuego se cierra por error de memoria.

2.3. Estructuras Estáticas (Arrays) vs. Dinámicas (Listas, Pilas y Colas)

Con este mapa en mente, distinguimos dos familias de estructuras lineales:

  • Estructuras de datos estáticas (el Array clásico T[]): La cantidad de memoria que ocupan se fija al crearlas y no puede cambiar. Por ejemplo, new string[6] reserva exactamente 6 casillas pegadas en memoria.
    • Ventaja: Como las casillas están contiguas, el procesador las lee a velocidad ultrarrápida y podemos saltar a cualquier casilla array[i] en tiempo constante $O(1)$.
    • Problema: Si no sabemos de antemano cuántos enemigos o proyectiles habrá en pantalla, un array fijo se quedará corto (provocando un error al intentar meter uno más) o, si reservamos 10.000 casillas «por si acaso», desperdiciaremos memoria durante toda la partida.
  • Estructuras de datos dinámicas (Listas, Pilas y Colas): Su tamaño no queda fijado de antemano. Solicitan espacio a la Memoria Libre a medida que el jugador recoge objetos o aparecen enemigos, y lo sueltan cuando ya no se necesitan.

2.4. Devolver la Memoria Libre: Recogida de Basura (Garbage Collector)

Mientras que la Pila de Ejecución se limpia sola al terminar cada método, ¿qué ocurre con los datos que creamos en la Memoria Libre cuando ya no nos hacen falta (por ejemplo, cuando eliminamos un nodo de una lista)?

  • Enfoque explícito (manual): En lenguajes como C o C++, es responsabilidad del programador devolver manualmente cada bloque a la memoria libre. Si el programador se olvida, esa memoria queda bloqueada para siempre (fuga de memoria o memory leak).
  • Enfoque implícito (Recogida de Basura / Garbage Collection): Es el enfoque que utiliza C# en Unity. Cuando desconectamos un elemento de una lista o cola dinámica y ninguna variable apunta ya a él, ese bloque queda «huérfano» en la Memoria Libre. Periódicamente, un sistema automático de C# llamado Recolector de Basura (Garbage Collector o GC) rastrea la Memoria Libre, detecta esos datos abandonados y los limpia para recuperar espacio.
Problema del Garbage Collector

Aunque el Recolector de Basura de C# nos ahorra liberar la memoria a mano, no es gratis. Cada vez que la Memoria Libre acumula demasiada «basura» (nodos eliminados, listas temporales creadas dentro del método Update() en cada fotograma), el Recolector de Basura ralentiza la ejecución del juego para limpiar la RAM, esto puede afectar a la performance. Por eso, en videojuegos usamos Arrays fijos cuando conocemos el tamaño máximo, y Listas/Colas dinámicas solo cuando el volumen de datos es realmente variable, evitando crear y destruir estructuras nuevas en cada fotograma.

3. Construcción de nuestras propias Estructuras Lineales

Ahora que conocemos la teoría de TADs y el mapa de memoria, vamos a construir desde cero nuestras propias estructuras lineales en C# para entender qué ocurre exactamente cuando encapsulamos bien.

3.1. Lista Basada en Array (Cómo funciona List por dentro)

¿Cómo podemos crear una lista donde el jugador pueda meter elementos sin límite si los arrays de C# tienen tamaño fijo? El truco consiste en guardar un array privado y, cuando se llene, crear (en la Memoria Libre porque ya se estaría ejecutando el juego) un array nuevo con el doble de capacidad, copiar los datos antiguos y desechar el array viejo (que recogerá el Garbage Collector).

Además, si queremos insertar o borrar un objeto en mitad de la lista sin dejar huecos vacíos, tendremos que empujar (desplazar) todos los elementos siguientes una casilla hacia la derecha o hacia la izquierda, lo que tiene un coste lineal $O(n)$:

public class MiListaArray {
    private string[] datos;
    private int cantidad;

    public MiListaArray(int capacidadInicial = 4) {
        datos = new string[capacidadInicial];
        cantidad = 0;
    }

    public int Cantidad() {
        return cantidad;
    }

    // Acceso directo e instantáneo: Coste O(1)
    public string Obtener(int indice) {
        if (indice < 0 || indice >= cantidad) return null;
        return datos[indice];
    }

    // Añadir al final: Coste O(1) casi siempre, O(n) si toca duplicar el array
    public void Añadir(string nuevoDato) {
        if (cantidad == datos.Length) {
            DuplicarCapacidad();
        }
        datos[cantidad] = nuevoDato;
        cantidad++;
    }

    // Insertar en una posición intermedia: Coste O(n) por desplazar elementos
    public void InsertarEn(int indice, string nuevoDato) {
        if (indice < 0 || indice > cantidad) return;

        if (cantidad == datos.Length) {
            DuplicarCapacidad();
        }

        // Desplazamos los elementos una casilla a la derecha para abrir hueco
        //Aqui recorremos el array al reves para asi olvidarnos de no pasarnos con el indice
        for (int i = cantidad; i > indice; i--) {
            datos[i] = datos[i - 1];
        }

        datos[indice] = nuevoDato;
        cantidad++;
    }

    // Eliminar de una posición intermedia: Coste O(n) por tapar el hueco
    public void EliminarEn(int indice) {
        if (indice < 0 || indice >= cantidad) return;

        // Desplazamos los elementos a la izquierda para tapar el hueco
        for (int i = indice; i < cantidad - 1; i++) {
            datos[i] = datos[i + 1];
        }

        cantidad--;
        datos[cantidad] = null; // Evitamos retener basura en memoria
    }

    // Rutina privada auxiliar: pide un bloque el doble de grande en Memoria Libre
    private void DuplicarCapacidad() {
        string[] nuevoArray = new string[datos.Length * 2];
        for (int i = 0; i < cantidad; i++) {
            nuevoArray[i] = datos[i];
        }
        datos = nuevoArray; // El array antiguo queda para el Garbage Collector
    }
}

3.2. Lista Enlazada (MiListaEnlazada) con Nodos en Memoria Libre

Para evitar el coste de redimensionar arrays o desplazar cientos de casillas cada vez que insertamos o cambiamos de sitio un elemento en mitad de una secuencia, podemos diseñar una estructura 100% dinámica: la Lista Enlazada.

En una lista enlazada los datos no están pegados en la memoria. Cada elemento vive dentro de un objeto llamado Nodo que se aloja en cualquier hueco disponible de la Memoria Libre. Cada nodo guarda dos cosas:

  1. El dato (por ejemplo, el nombre de un ataque o carta).
  2. Una referencia o enlace (siguiente) que apunta a la dirección de memoria donde se encuentra el próximo nodo de la lista (o null si es el último).
// Cada Nodo es una pieza independiente en la Memoria Libre (Heap)
public class Nodo {
    public string dato;
    public Nodo siguiente;

    public Nodo(string datoNodo) {
        dato = datoNodo;
        siguiente = null;
    }
}

public class MiListaEnlazada {
    //Protegemos la referencia al primero
    private Nodo cabeza;
    private int cantidad;

    public MiListaEnlazada() {
        cabeza = null;
        cantidad = 0;
    }

    public int Cantidad() {
        return cantidad;
    }

    // Insertar al principio es instantáneo O(1): ¡no desplazamos nada!
    public void InsertarAlPrincipio(string nuevoDato) {
        Nodo nuevoNodo = new Nodo(nuevoDato);
        nuevoNodo.siguiente = cabeza; // El nuevo nodo apunta a la antigua cabeza
        cabeza = nuevoNodo;           // La cabeza pasa a ser el nuevo nodo
        cantidad++;
    }

    // Insertar al final recorriendo los enlaces: Coste O(n)
    public void InsertarAlFinal(string nuevoDato) {
        Nodo nuevoNodo = new Nodo(nuevoDato);

        if (cabeza == null) {
            cabeza = nuevoNodo;
        } else {
            Nodo actual = cabeza;
            // Avanzamos siguiendo las flechas hasta llegar al último nodo
            while (actual.siguiente != null) {
                actual = actual.siguiente;
            }
            actual.siguiente = nuevoNodo;
        }
        cantidad++;
    }

    // Eliminar la primera aparición de un dato puenteando su enlace
    public bool Eliminar(string datoBuscado) {
        if (cabeza == null) return false;

        // Caso especial: el nodo a borrar es la propia cabeza
        if (cabeza.dato == datoBuscado) {
            cabeza = cabeza.siguiente; // El antiguo primer nodo queda para el GC
            cantidad--;
            return true;
        }

        Nodo actual = cabeza;
        while (actual.siguiente != null) {
            if (actual.siguiente.dato == datoBuscado) {
                // Puenteamos el nodo a eliminar: el anterior apunta al siguiente del borrado
                actual.siguiente = actual.siguiente.siguiente;
                cantidad--;
                return true;
            }
            actual = actual.siguiente;
        }
        return false;
    }
}
La metáfora del tren de mercancías

Una Lista Enlazada es como un tren donde cada vagón (Nodo) solo sabe a qué vagón tiene enganchado detrás (siguiente). Si quieres meter un vagón nuevo en medio, no tienes que construir un tren nuevo: simplemente desenganchas el acople entre dos vagones y enganchas el nuevo en medio en tiempo $O(1)$. A cambio, si quieres saber qué lleva el vagón número 5, no puedes saltar directamente a él como en un array; tienes que entrar por la locomotora (cabeza) y caminar vagón por vagón ($O(n)$).

3.3. TADs Lineales con Reglas Especiales: La Pila (LIFO) y la Cola (FIFO)

Muchas mecánicas de los videojuegos no necesitan insertar ni buscar elementos en mitad de una lista, sino que funcionan bajo un orden estricto de entrada y salida. Restringiendo las operaciones de una lista obtenemos dos TADs clásicos:

A) El TAD Pila (Stack - LIFO: Last In, First Out)

En una Pila (como una pila de platos o un mazo de cartas boca abajo), el último elemento en entrar es siempre el primero en salir. Solo podemos interactuar con la cima de la pila mediante dos operaciones de coste $O(1)$:

  • Apilar(dato) (Push): Coloca un elemento nuevo encima de la cima.
  • Desapilar() (Pop): Retira y devuelve el elemento que está en la cima.

Aplicación en Unity: El botón de «Deshacer movimiento» (Undo) en un juego de puzles táctico. Cada vez que el jugador se mueve, apilamos su casilla anterior; si pulsa Deshacer, desapilamos la cima y el personaje retrocede exactamente por el camino inverso:

// Implementación dinámica de una Pila de movimientos usando Nodos enlazados
public class MiPilaMovimientos {
    private Nodo cima; // Apunta siempre al último elemento apilado

    public bool EstaVacia() {
        return cima == null;
    }

    // Apilar (Push): Coste O(1)
    public void Apilar(string movimiento) {
        Nodo nuevo = new Nodo(movimiento);
        nuevo.siguiente = cima;
        cima = nuevo;
    }

    // Desapilar (Pop): Coste O(1)
    public string Desapilar() {
        if (EstaVacia()) return null;

        string ultimoMovimiento = cima.dato;
        cima = cima.siguiente; // La cima baja al plato inferior
        return ultimoMovimiento;
    }
}
B) El TAD Cola (Queue - FIFO: First In, First Out)

En una Cola (como la fila del cine), el primer elemento en llegar es el primero en salir. Los elementos nuevos entran siempre por el final y se extraen por el frente (principio), ambos en tiempo constante $O(1)$ si guardamos una referencia a ambos extremos:

  • Encolar(dato) (Enqueue): Añade un elemento al final de la cola.
  • Desencolar() (Dequeue): Extrae y devuelve el elemento que lleva más tiempo esperando en el frente.

Aplicación en Unity: Un generador de oleadas de enemigos (Wave Spawner) o una cola de cuadros de diálogo de un NPC:

// Implementación dinámica de una Cola guardando el frente y el final
public class MiColaEnemigos {
    private Nodo frente; // Por donde salen (Dequeue)
    private Nodo final;  // Por donde entran (Enqueue)

    public bool EstaVacia() {
        return frente == null;
    }

    // Encolar al final: Coste O(1)
    public void Encolar(string tipoEnemigo) {
        Nodo nuevo = new Nodo(tipoEnemigo);
        if (EstaVacia()) {
            frente = nuevo;
            final = nuevo;
        } else {
            final.siguiente = nuevo;
            final = nuevo;
        }
    }

    // Desencolar por el frente: Coste O(1)
    public string Desencolar() {
        if (EstaVacia()) return null;

        string enemigoSiguiente = frente.dato;
        frente = frente.siguiente;

        // Si la cola se ha quedado vacía, limpiamos también la referencia final
        if (frente == null) {
            final = null;
        }
        return enemigoSiguiente;
    }
}

4. Ejercicios de estructuras lineales y TADs

Aplica los conceptos de encapsulación, arrays estáticos y estructuras dinámicas implementando en C# las siguientes propuestas para Unity:

  1. Especificación y TAD Cargador de Munición: Diseña y programa la clase CargadorTAD respetando la encapsulación (variables private y métodos public). Debe almacenar hasta un máximo fijo de $N$ balas usando un array e incluir las rutinas de acceso Disparar(), RecargarUnaBala(), RecargarCompleto() y BalasRestantes().
